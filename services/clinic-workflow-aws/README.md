# ClinicPluz synthetic staging clinic workflow

This service implements staff reception and a first nurse-to-doctor consultation flow behind the existing staff sign-in. Reception, consultation, and a fictional medicine shortlist item passed Goodwell synthetic staging checks by 2026-10-10. Patient history was deployed to synthetic Goodwell staging on 2026-10-11; the unauthenticated history route returned `401`, and the owner confirmed the doctor-only section appears. A populated-history browser test remains pending. None of these slices is ready for real clinic records. The shared product contracts are in `docs/CLINIC_WORKFLOW_V1.md`, `docs/CONSULTATION_V1.md`, and `docs/PATIENT_HISTORY_V1.md`.

The structured medicine timing and reception/pharmacy handoff routes were deployed to synthetic Goodwell staging on 2026-10-14. A signed-out handoff request returned `401`; the signed-in cross-role flow still needs live verification. Synthetic PDF email remains disabled by default pending a separately reviewed SES setup.

The billing routes below are **local implementation only** as of 2026-10-15. They have not been deployed or connected to real payments, taxes, or patient records.

## API and access boundary

The same-origin routes are under `/api/workflow/clinics/:slug`:

| POST | `/consultations/draft` | `consultations` | Assigned doctor saves notes and medication entries |

Every route requires the existing opaque `__Host-cpz_session` cookie and independently checks its hash in the auth table, expiry, clinic path, active clinic, active membership, Cognito user state, role, and the clinic's `ENTITLEMENTS` record. Only `clinic_admin`, `receptionist`, and `nurse` can access these first reception routes. Missing or disabled entitlement fails closed. POST additionally requires the exact configured `Origin` and the session's `X-CSRF-Token`; patient search is POST so names and phone numbers stay out of URLs. All responses are JSON with `Cache-Control: no-store`. No browser-supplied clinic ID, role, or entitlement grants access.

The consultation routes are separate clinician permissions: `nurse` can see the clinic queue, read patient identity and vitals, and record vitals; `doctor` sees only appointments whose persisted doctor roster item has `staffSub` equal to that doctor's authenticated Cognito `sub`. Only that doctor can read, draft, and finalize clinical notes and prescription entries for those appointments. A nurse's read response omits notes, medication entries, and print data. `clinic_admin`, receptionist, lab, billing, and pharmacist roles have no general consultation access, even if an entitlement is enabled. The two dedicated prescription handoff routes allow clinic admin, receptionist, and pharmacist sessions to see finalized medication orders; they never return clinical notes or vitals. Only clinic admin and receptionist roles can access the separate synthetic email preview/send routes. An old entitlement map without `consultations` is interpreted as disabled for consultation while reception continues to work. The browser cannot supply `staffSub` or a doctor role.

### Local synthetic billing contract

Billing is a separate optional `billing` entitlement; absent means disabled and does not affect older reception routes. `clinic_admin` and `receptionist` can check in, add the one-time fee, view bills, record payments, and issue the final receipt. Only `pharmacist` can read/post fulfillment, and also needs `consultations`. Doctor, nurse, lab, and generic billing roles have no billing access in this pilot. Every write uses the existing session, clinic, Origin, CSRF, Cognito, and CloudFront edge checks. Responses are `no-store`; patient identifiers remain in JSON bodies.

All POST requests below include `appointmentId` and `clinicDate` in the body. A mutation also includes a fresh UUIDv4 `operationId`; a replay of the *same* operation and payload returns the existing result, while reuse with different content conflicts. Expected bill revisions protect against concurrent changes; stale revisions return `409`. No clinical note, vital, patient phone, or email is included in a billing response.

| Route | Additional JSON request | Success |
| --- | --- | --- |
| `GET /billing/config` | none | `{currency:"INR",consultationFeePaise,version}` |
| `POST /appointments/check-in` | `{operationId,expectedFeePaise}` | `{appointment:{...status:"checked_in"},episode}`; booked phone visits become checked in atomically with the fee, while walk-ins already checked in can confirm the fee |
| `POST /billing/consultation-charge` | `{operationId,expectedFeePaise,reason:"legacy_check_in_missing"}` | `{episode}`; a checked-in visit or older booked visit with a finalized encounter can receive its missing fee once |
| `GET /billing/episodes?date=YYYY-MM-DD` | none | `{items:Episode[]}` for persisted episodes only; use `/appointments` to find older visits with no bill |
| `POST /billing/read` | none | `{episode,charges,payments,receipt}`; no episode returns `404` |
| `POST /billing/fulfillment/read` | none | `{appointmentId,clinicDate,patient:{id,fullName},prescriptionRevision,items,episode}`; before the first write the episode is a read-only `revision:0` preview |
| `POST /billing/fulfillment` | `{operationId,expectedRevision,prescriptionRevision,items:[{prescriptionIndex,quantity,quantityUnit,unitPricePaise,status}],closeForCheckout}` | `{episode}`; multiple distinct exact Rx indexes per request, or empty items with `closeForCheckout:true` to attest no purchase |
| `POST /billing/payments` | `{operationId,expectedRevision,amountPaise,method:"cash"|"upi"|"card",reference?}` | `{episode,payment}` |
| `POST /billing/receipt` | `{operationId,expectedRevision}` | `{episode,receipt}` after consultation finalized, pharmacy closed if Rx has medicines, one-time fee posted, and balance zero |

`Episode` has `appointmentId`, `clinicDate`, `patientId`, `patientName`, `currency`, `revision`, `consultationTotalPaise`, `pharmacyTotalPaise`, `totalPaise`, `paidPaise`, `outstandingPaise`, `pharmacyDisposition` (`awaiting|open|closed|not_required`), `checkoutStatus` (`awaiting_fee|awaiting_consultation|awaiting_pharmacy|ready_for_checkout|partly_paid|paid`), `receiptIssued`, `createdAt`, and `updatedAt`. Even a fully paid consultation fee remains **open** while the doctor/pharmacy outcome is unknown. `paid` appears only after the immutable receipt is issued. Pharmacy-first visits show `awaiting_fee`, not ready for checkout.

The pharmacist sees each canonical finalized prescription item's `prescriptionIndex`, doctor-entered `name` and `strength`, prior `supplies`, `suppliedQuantity`, `quantityUnit`, and a pharmacist-attested `status` (`not_supplied|partly_supplied|supplied`). `remainingQuantity` is `null` because the current clinical Rx does not carry a numeric prescribed quantity. Fulfillment accepts integer quantity 1–10,000, one of `tablet|capsule|ml|g|piece|pack`, integer unit price 0–10,000,000 paise, and a line total up to 100,000,000 paise. Multiple events can record a partial fill; each index's cumulative quantity is capped at 10,000 and its unit cannot silently change. `status` is chosen by the pharmacist, never inferred as dose or treatment advice. A different product cannot be substituted through this API. Only actual supplied `quantity × unitPricePaise` becomes a charge. Closing the disposition prevents further supply in this slice.

Charge rows have `id`, `kind`, `description`, `quantity`, `quantityUnit`, `unitPricePaise`, `amountPaise`, `source`, optional `prescriptionIndex`/`prescriptionRevision`, `createdAt`, and `actorSub`. Payment rows have `id`, `amountPaise`, `method`, `reference`, `recordedAt`, and `actorSub`. The receipt freezes clinic/patient identity, charge and payment snapshots, totals, issuer, and issue time under `label:"SYNTHETIC DEMO RECEIPT"`. It is **not** a statutory invoice, tax calculation, or bank-verified payment. Adjustments, discounts, refunds, substitutions, and corrections after issue require later reviewed workflows; this first slice rejects later bill changes.

One strongly consistent tenant+appointment bill partition holds the episode, append-only charges/fulfillment/payments, operation fingerprints, and a single receipt. A tenant+date index supports the bounded reception list. Every mutation uses a DynamoDB transaction: appointment/encounter/config conditions when relevant, episode revision compare-and-swap, child item, operation record, date index, and metadata-only audit. A retry with an uncertain response checks the durable operation record before returning; no duplicate fee, pharmacy line, payment, or receipt is posted. The pilot caps a visit at 50 charge lines, 30 payments, and 30 supply events (plus one empty close), and reads at most 250 visit rows and 200 date episodes; overflow fails closed rather than scanning. All data is synthetic staging only.

For a **synthetic Goodwell setup after review**, preserve the existing auth `CLINIC#goodwell / ENTITLEMENTS` map and add boolean `modules.billing=true`; leave `patient_intake`, `appointments`, `consultations`, and other keys intact. In the existing clinical table, set one clinic-owned configuration record: `pk=CLINIC#goodwell#CONFIG`, `sk=BILLING`, `currency` String `INR`, `consultationFeePaise` Number `200000`, and `version` Number `1`. The fee is a per-clinic server record, never a global constant or browser override. These two settings enable the pilot after the reviewed deployment; this README does not create them or authorize entering real billing data.

### Clinic medicine shortlist

The doctor can search a **clinic-specific** shortlist while entering a prescription. Search fills only the selected item's name and strength; dose, route, frequency, duration, and instructions remain doctor-entered. The doctor can edit any populated text or enter a medicine manually when no item matches. A `favorite` flag sorts clinic-preferred items first, but is not a treatment recommendation. This does not perform medicine safety checks.

`POST /consultations/medicines/search` accepts only `{ "query": "..." }` with 2–64 letters/numbers and common name punctuation, after whitespace normalization. It returns at most 20 active matches as `{ "items": [{ "id", "name", "strength", "favorite" }] }`. It requires the existing doctor role, consultation entitlement, session, clinic match, Origin, and CSRF checks. No medicine text appears in the URL.

For the synthetic pilot, operators may create shortlist items in the existing **clinical** DynamoDB table. Each item has `pk` (String) = `CLINIC#goodwell#MEDICINES`, `sk` (String) = `MEDICINE#<unique-id>`, `id` (String) = the same unique ID, `name` (String, including dosage form when applicable), `strength` (String), `active` (Boolean) = `true`, and optional `favorite` (Boolean). Use only fictitious medicine names in staging. There is no global medicine list or automatic import. The pilot caps each clinic partition at 200 items; exceeding that limit fails closed. Catalogue scaling is on hold while the product owner decides how medicine data will be managed; manual entry remains available.

### Exact consultation JSON contract

All consultation POST requests have `Content-Type: application/json`, an exact public `Origin`, and the authenticated `X-CSRF-Token`; identifiers go in the body, never in a URL. `appointmentId` is the server-issued appointment UUID and `clinicDate` is its local `YYYY-MM-DD` date. The server uses them only to look up the persisted appointment in the path clinic; it derives patient and doctor IDs from that row and verifies the patient and assigned roster doctor before returning clinical data.

| Method/path suffix | JSON request | Success |
| --- | --- | --- |
| `GET /consultations?date=YYYY-MM-DD` | none | `{ "items": [{ "appointmentId", "clinicDate", "patientId", "patientName", "doctorId", "doctorName", "startAt", "appointmentStatus", "encounterStatus" }] }` |
| `POST /consultations/read` | `{ "appointmentId", "clinicDate" }` | `{ "encounter": { ... } }` |
| `POST /consultations/medicines/search` | `{ "query" }` | `{ "items": [{ "id", "name", "strength", "favorite" }] }` |
| `POST /consultations/vitals` | `{ "appointmentId", "clinicDate", "expectedRevision", "vitals": { "observedAt", "systolicBpMmHg"?, "diastolicBpMmHg"?, "pulseBpm"?, "spo2Percent"?, "temperatureC"?, "weightKg"?, "heightCm"? } }` | `200` with updated `{ "encounter": { ... } }` |
| `POST /consultations/draft` | `{ "appointmentId", "clinicDate", "expectedRevision", "note": { "chiefComplaint", "history", "exam", "assessment", "plan" }, "medications": [{ "name", "strength", "dose", "route", "frequency", "timing"?, "duration", "instructions" }] }` | `200` with updated `{ "encounter": { ... } }` |
| `POST /consultations/finalize` | `{ "appointmentId", "clinicDate", "expectedRevision" }` | `200` with finalized `{ "encounter": { ... } }` and print payload only if medications exist |

`encounter` contains `appointmentId`, `clinicDate`, `status` (`draft` or `finalized`), numeric `revision`, `vitals`, `finalizedAt`, and server-sourced `patient:{id,fullName,ageYears,sex}`, `doctor:{id,displayName}`, and `clinic:{slug,displayName}`. For an assigned doctor it also contains the five-field `note` and medication array. Before the first save, an authorized read returns an unsaved draft at revision `0`, `vitals:null`, empty note strings, empty medications, and `finalizedAt:null`. A nurse receives the shared encounter fields but **no** `note` or `medications` properties. `encounterStatus` in the queue is `draft` for an unsaved or draft encounter and `finalized` after finalization.

Vitals need at least one finite numeric measurement. Both blood-pressure values must be supplied together. Their property names carry explicit units; `observedAt` is an ISO timestamp with `Z` or an offset, while `recordedAt`, `recordedBySub`, and `recordedByDisplayName` come from the server and appear on subsequent reads. Technical input bounds reject malformed data but make no medical judgment. Notes are capped at 3,000 characters per field; medication entries at 20, with bounded text. Draft fields may be incomplete. `timing` may be omitted or `null` (legacy/free-text mode), or `{ "timesOfDay": ["morning"|"afternoon"|"night", ...], "mealRelation": "before"|"after"|"with"|"unspecified" }`. The list needs 1–3 distinct values; omitted `mealRelation` becomes `unspecified`. Reads always return `timing`, using `null` for older entries. Finalization requires a nonempty assessment and plan, explicit dose, route, duration and instructions, plus either nonempty free-text `frequency` or structured `timing`. It rejects both together to avoid contradictory duplicate directions. Neither time selection nor meal relation supplies a dose or treatment suggestion. Clinical decisions and medicine selection are entirely clinician-entered.

Every mutation increments `revision`; the caller must send the current `expectedRevision`. Stale writes and edits after finalization return `409`. Successful saves atomically write an audit event with actor, timestamp, action, and revision, without note or medicine text. Finalized encounters are immutable in this slice. `printablePrescription` is a **top-level sibling** of `encounter` only in an assigned doctor's read/finalize response when the server reports a finalized encounter with at least one medication. It contains `{clinic:{slug,displayName},doctor:{id,displayName},patient:{id,fullName,ageYears,sex},appointmentDate,finalizedAt,medications:[{name,strength,dose,route,frequency,timing,duration,instructions}]}`. It is omitted for drafts, nurse reads, and finalized encounters without medication. The browser must escape clinician-entered text when rendering and print only this server-confirmed payload. The separate demo email flow renders its own server PDF; it never trusts browser-rendered print content.

### Reception and pharmacy prescription handoff

These dedicated routes require an active `receptionist` or `pharmacist` membership plus the clinic's `consultations` entitlement. They do **not** authorize the general consultation queue, note, vital, draft, finalize, history, or medicine-search routes. The pharmacist has no patient intake or appointment booking permission. Both handoff routes use the same clinic session and origin-only edge boundary as the rest of the service; the POST also requires exact Origin and CSRF. Responses are `no-store`, and no patient identifiers appear in a prescription-read URL.

| Route | Request | Response |
| --- | --- | --- |
| `GET /consultations/prescriptions?date=YYYY-MM-DD` | One clinic-local date | `{ "items": [{ "appointmentId", "clinicDate", "patientId", "patientName", "doctorId", "doctorName", "startAt", "finalizedAt" }] }` |
| `POST /consultations/prescriptions/read` | `{ "appointmentId", "clinicDate" }` | `{ "status": "finalized", "printablePrescription": { "clinic", "doctor", "patient", "appointmentDate", "finalizedAt", "medications" } }` |

The queue only includes finalized encounters containing at least one medication. It lists up to the existing 200-appointment clinic-day bound and verifies each candidate's canonical encounter in batches of 20; a broken finalized pointer fails closed. The detail route resolves the persisted appointment and patient in the path clinic, then checks the canonical finalized encounter's patient, doctor, appointment and frozen clinician identity. Drafts, missing encounters, and finalized encounters without medication return `404`. Queue and detail omit notes, vitals, phone, email, and all draft medicines. Existing finalized medicines without a structured timing field display `timing:null`. The doctor's frozen finalizer name is used even if the roster label changes. This is a read-only operational handoff, not legal prescription or dispensing authorization.

### Default-off synthetic PDF email

Only a receptionist can use these POST routes. They require the usual session, active clinic and membership, Cognito check, `consultations` entitlement, exact Origin, CSRF, and the CloudFront origin-only header. The preview checks the same persisted appointment, patient, and canonical finalized prescription as the print read. It returns the **stored** full patient email for explicit receptionist verification in a no-store body; do not log it in browser telemetry. A missing patient email returns `409`, while drafts and finalized encounters without medication return `404`.

| Route | JSON request | Success |
| --- | --- | --- |
| `POST /consultations/prescriptions/email/preview` | `{ "appointmentId", "clinicDate" }` | `200 { "status":"ready", "recipientEmail":"stored@example.test", "recipientMasked":"s***@example.test" }` |
| `POST /consultations/prescriptions/email` | `{ "appointmentId", "clinicDate", "expectedRecipientEmail":"stored@example.test", "confirmPatientEmail":true }` | `202 { "status":"accepted", "recipientMasked":"s***@example.test" }` after SES accepts; duplicate accepted requests return `200` |

Send re-reads the patient email and rejects a changed value with `409`; `expectedRecipientEmail` is comparison-only and is **never** used as the destination. The one-shot delivery claim also conditionally checks the stored email and finalized encounter revision in the same DynamoDB transaction, closing a change between the read and claim. Browser-supplied recipient, PDF, medicine data, and sender are rejected. A PDF is generated in memory from the finalized prescription projection only, with a conspicuous synthetic-demo mark, bounded pages and size. The demo font currently supports ASCII text; unsupported patient/doctor/medicine characters fail closed with `422` so the receptionist can use browser print instead. No notes, vitals, phone numbers, or email addresses enter the PDF, audit records, or application logs. The attachment is not stored in S3 or returned to the browser.

Email is disabled by default. In the **staging** stack only, `EnablePrescriptionDemoEmail=true` requires `PrescriptionSenderEmail` to be SES-verified in the stack's Region and `PrescriptionAllowedRecipientEmail` to be one verified synthetic test inbox. Template parameter rules reject enabling the flag outside staging or leaving either address empty. The persisted patient email must match that allowed inbox exactly; mismatch returns `409`. The conditional SES IAM policy still requires the exact sender and recipient; its resource is temporarily `*` to diagnose a live SESv2 `AccessDeniedException` with the sender identity ARN. Review the result and narrow the resource before production. Keep the flag false for all other environments. SES sandbox rules may require verifying the recipient separately. The SDK has automatic retries disabled because SES has no send idempotency token. A clinic+appointment+final revision delivery claim and metadata-only audit event are written atomically before SES. Repeated requests do not re-send. A timeout or unclear outcome becomes `unknown` and returns `409` on later requests; it needs manual review. `accepted` means SES accepted the message for processing, **not** that the patient received it. Bounce/delivery event tracking, operational reconciliation, and privacy/legal review are still needed before real patient email.

Finalization freezes the authenticated doctor's staff `sub`, staff display name, and appointment doctor ID inside the encounter. Later roster or staff-profile renaming cannot change the clinician shown on a reprint. A doctor whose roster assignment is removed loses access; another doctor who inherits that roster mapping cannot read the already finalized encounter because its finalizer `sub` differs. This identity snapshot improves attribution in the synthetic pilot but does not establish legal prescription readiness or verified clinician credentials.

### Patient history JSON contract

Only the doctor **currently assigned to the selected appointment** can use these read-only POST routes. The service resolves that appointment from the clinic table, checks its active doctor roster `staffSub` against the authenticated Cognito identity, and derives the patient ID from the persisted appointment. If the selected encounter is finalized, its frozen finalizer `sub` must also match: reassigning the roster does not grant a different doctor history access through that appointment. The clinician on an earlier visit may be a different doctor. Nurse, receptionist, and clinic-admin sessions are denied. Both requests require the usual same-origin `Origin`, CSRF token, session, and `consultations` entitlement; all identifiers stay in the JSON body.

| Route | JSON request | Success |
| --- | --- | --- |
| `POST /consultations/history/list` | `{ "appointmentId", "clinicDate", "cursor"? }` | `{ "items": [{ "historyId", "clinicSlug", "patientId", "status":"finalized", "visitAt", "finalizedAt", "doctor": { "id", "displayName" } }], "nextCursor": string \| null, "coverage":"indexed_finalizations_only" }` |
| `POST /consultations/history/detail` | `{ "appointmentId", "clinicDate", "historyId" }` | `{ "history": { "historyId", "clinicSlug", "patientId", "status":"finalized", "visitAt", "finalizedAt", "doctor": { "id", "displayName" }, "vitals": object \| null, "note": { "chiefComplaint", "history", "exam", "assessment", "plan" }, "medications": [...] } }` |

`visitAt` is the historical appointment's persisted timezone-bearing start time, not the date of finalization. The fixed page size is 10, newest earlier visit first. `historyId` and `cursor` are opaque body-only values. The cursor is HMAC-signed with a patient-history domain label, bound to the clinic, derived patient, selected appointment and cutoff, and expires after 15 minutes; invalid or replayed context returns `400`. The list excludes the selected visit, visits at or after its start, and drafts. Detail checks the patient-scoped pointer and the canonical encounter's finalized state and frozen clinician identity before returning note, vitals, and medication text. It never returns a print payload or changes the current draft. A missing current appointment or historical pointer returns `404`; failed doctor assignment returns `403`; unavailable or inconsistent records fail closed.

On finalization, one transaction writes the canonical encounter, a clinical-text-free audit event, and a metadata-only pointer with `pk=CLINIC#<slug>#PATIENT#<patientId>#HISTORY` and `sk=VISIT#<appointment-start-UTC>#APPOINTMENT#<appointmentId>`. A strongly consistent reverse DynamoDB query reads at most 11 pointers per page; at most 11 canonical encounters are verified before returning 10. There is no table scan or date-wide history search. Older **finalized staging encounters** created before this pointer existed are not visible until a reviewed backfill creates and verifies their pointers. `coverage:"indexed_finalizations_only"` signals that the API is not asserting a complete longitudinal record. Do not backfill real clinical data or expose this feature for real use without privacy and retention review.

An origin-only `X-ClinicPluz-Edge-Key` is checked before the session lookup. It is a boundary for the public API Gateway endpoint, not a substitute for staff authorization. Store it only in Secrets Manager and a CloudFront origin custom header. Do not send it from the browser or commit it. The service currently accepts a single exact `https://*.cloudfront.net` public origin for the synthetic staging host; owned clinic subdomains need a separately reviewed host-routing design.

## Separate data store and appointment behavior

`template.yaml` declares a dedicated DynamoDB clinical table with encryption, point-in-time recovery, and a retained deletion policy. It reads sessions, clinic status, memberships, and entitlements from the existing auth table; it never writes clinical records there. Clinical table partition keys start with `CLINIC#<slug>`. Registration transactionally writes one patient record, two bounded search lookups, and a PII-free audit event. Booking transactionally checks the patient and active doctor, claims a unique doctor/UTC-start slot, and writes the appointment and audit event. A competing booking for the same doctor slot returns `409` without a partial appointment.

Phone bookings start as `booked`; walk-ins start as `checked_in`. Both use the same 30-minute doctor slots and appear in the date list. A slot that has already ended is rejected; a walk-in may use the currently running slot. The pilot schedule is read per clinic from the clinical table. It is provisionally `Asia/Kolkata`, 09:30–18:30, with `:00` and `:30` starts and 18:00 as the last start. The service does not infer opening hours from the browser.

## Required synthetic setup before a connected test

The stack does **not** create clinic schedules, doctors, patients, or entitlements. Without the schedule item, appointment creation returns `503`; without an active doctor it cannot book; without `ENTITLEMENTS` every workflow route returns `403`. Goodwell's synthetic intake and appointment entitlements were exercised in the 2026-10-10 staging smoke test. An operator must review the following **synthetic** records for a clinic such as `goodwell`:

1. In the existing **auth table**, keep the clinic `CLINIC#goodwell / META` and staff `CLINIC#goodwell / STAFF#<username>` records established by `clinic-auth-aws`. Add or update the `CLINIC#goodwell / ENTITLEMENTS` item with string `clinicSlug=goodwell` and a DynamoDB map `modules` containing boolean `patient_intake=true` and `appointments=true`. Preserve any other module keys already managed by the Control Panel; do not replace its record blindly. A suitable active receptionist, nurse, or clinic admin membership and Cognito account are also required.
2. In the new **clinical table**, create one schedule item with `pk=CLINIC#goodwell#CONFIG`, `sk=SCHEDULE`, string `timezone=Asia/Kolkata`, numeric `openMinute=570`, numeric `closeMinute=1110`, and numeric `slotMinutes=30`. These are minutes after local midnight, so 570 is 09:30 and 1110 is 18:30. Treat this as pilot configuration, not a default for every clinic.
3. In the clinical table, create at least one synthetic active doctor item with `pk=CLINIC#goodwell#DOCTORS`, `sk=DOCTOR#doctor-001`, string `id=doctor-001`, string `displayName=Dr Demo`, and boolean `active=true`. The `id` must match the suffix after `DOCTOR#`. A reception-only roster entry can omit the consultation staff mapping below.

## Checks and limits

The Lambda target is Node.js 22. The source-level test command uses experimental TypeScript stripping, so use Node.js 24 for `npm test`; run `npm run typecheck` after installing dependencies. The tests cover cross-clinic denial, role and entitlement gates, Cognito revocation, CSRF and private search, schedule boundaries, appointment conflict, doctor queue scoping, nurse vitals, doctor draft/finalization, print availability, stale revision, malformed input, clinic medicine search, patient-history isolation, the default-off demo email, and local synthetic billing authorization/state transitions. The history update passed `sam build` and reached the existing staging workflow stack. Its unauthenticated route returned `401`; a live, populated-history read against DynamoDB remains unverified. The handoff routes and default-off email code reached the staging workflow stack on 2026-10-14. Signed-in receptionist/pharmacist behavior and browser print still need live verification; demo email remains disabled. Billing has **not** been built with SAM or deployed.

This slice deliberately omits cancellation, rescheduling, doctor shifts, holidays, correction/addendum to finalized notes, clinical signatures/credentials, live payment integration, tax invoicing, refunds, and general patient email dispatch. Search keys currently include plaintext normalized names and phone digits, and lookup rows duplicate patient fields. No real clinic or patient data should be entered into this synthetic staging service.
